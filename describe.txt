## Product concept

The central interface is a clean, schematic subway map. Subway lines are solid, thick, coloured lines, with circular station nodes sitting directly on top of them.

The map is not an editor. Users cannot drag stations, reconnect lines, delete elements, or change the layout. They may only pan, zoom, click stations, and use selection controls.

Users select stations that they want monitored. Their selected stations do not need to form a valid or continuous route.

## Selection behaviour

Use one manual-selection mode rather than separate “route” and “manual” modes.

* Clicking an unselected station selects it.
* Clicking a selected station deselects it.
* Selected stations are clearly highlighted.
* When a station is selected, up, down, left and right arows
on the keyboard can be used to select quickly stations in set direction.
* Selection must follow the ordered station data for that line.
* Interchange stations require line-aware direction controls so the system does not select an ambiguous branch.
* Users can still add or remove any individual stations afterward.
* Display the number of selected stations.
* Provide a clearly visible “Clear all” action.
* Make the controls keyboard-accessible and usable on mobile devices.

Do not implement route-finding or require selected stations to be connected.

## Monitoring panel

Place a compact configuration panel in the upper-right corner on desktop. It may become a drawer or bottom sheet on small screens.

The panel should include:

* Selected-station count
* Selected-station summary
* Start time
* End time
* Time-zone-aware handling
* Weekday selection for Monday through Sunday
* Email address
* Consent checkbox for receiving monitoring emails
* Save/subscribe button
* Clear-selection action
* Validation and understandable error messages
* Success confirmation after preferences are saved

A user should not need to create a password-based account. For the first version, they provide an email address and confirm ownership through a verification email or magic link. Do not expose saved preferences merely by accepting an unverified email address.

Include an unsubscribe and preference-management mechanism. Do not store unnecessary personal information.

## Visual direction

The application should feel like a polished public-transit product:

* Thick solid line colours
* Circular stations positioned directly over the lines
* Larger or double-ring interchange stations
* Clear station labels
* Strong selected, unselected, hover, and keyboard-focus states
* Minimal visual clutter
* Responsive layout
* Accessible colour contrast
* No React Flow editing controls or editor-like appearance

Do not rely on colour alone to indicate selection.

### Phase 7: Monitoring service

use this api from this website https://open.toronto.ca/dataset/ttc-gtfs-realtime-gtfs-rt/ 
to get real data. For TTC monitoring, the main source should be the official TTC GTFS-Realtime Service Alerts feed, published through Toronto Open Data.
Every few minutes, the backend would:

Download the latest service-alert feed.
Decode the GTFS-Realtime data.
Extract affected lines, routes, stops/stations, alert type, description, and active time.
Match each alert against users’ selected stations, weekdays, and time ranges.
Send an email only when a new matching alert appears.
Record that notification so the same alert is not repeatedly emailed.
Optionally send another message when the alert is removed and service resumes.
Important complication

TTC alerts will not always identify every affected station individually. An alert might say:

No subway service between Finch and Eglinton.

Our application would therefore need to understand the ordered subway network and expand that alert to all stations between those endpoints.

Other alerts may be associated only with an entire line. When station-level information cannot be determined confidently, we should either:

Notify everyone monitoring any station on that line and label it a line-level alert, or
Avoid sending it to station-specific subscribers.
Additional official data

We would also use the TTC’s static GTFS schedule/network data for official station IDs, route IDs, and stop relationships. The interactive map could have manually designed display coordinates, while retaining the official GTFS identifiers for matching alerts.

We should not scrape the TTC website or social-media posts as the primary source. The official GTFS-Realtime feed is more structured, reliable, and intended for applications. The TTC’s own service-alert page can be used as a human-readable link inside the notification. TTC live service alerts

One concern: TTC already offers broad email alerts through MyTTC e-Services. Your app’s useful distinction would be precise station selection plus chosen weekdays and monitoring hours, rather than duplicating general line alerts.
